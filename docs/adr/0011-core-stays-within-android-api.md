# 0011 `:core` で使う JDK API を Android の API 水準に収める

- 状態: 採用
- 日付: 2026-11-27
- 置換: なし（ADR 0007 を補足する）

## 文脈

ADR 0007 では、モデル・文書ストア・集計・抽出の決定論層を `:core` に置き、Android SDK を必要としない JVM テストを速く回せるようにした。しかし、`:app` に Android との境界を集め、`:core` から `android.*` を排除するだけでは、実行可能な API の境界までは決まらない。

`:core` をコンパイルする JDK の API 面は、Android の API 面より先に進む。JVM モジュールではホスト JDK にあるメソッドを普通に解決でき、`:core:test` もホスト JVM 上で成功する。そのコードを `:app` から呼んだとき、同じメソッドが `minSdk` の端末に存在するとは限らない。

実際に `DocumentStore` は `java.nio.file.Files.readString` / `writeString` を使っている。Android SDK の android-36 に含まれる `platforms/android-36/data/api-versions.xml` で確認した結果は次の通りである。

| API | android-36 の `api-versions.xml` での確認 |
| --- | --- |
| `java/nio/file/Files` | クラスは `since=26` で存在する |
| `Files.readAllBytes` / `Files.write` 系 | 存在する |
| `Files.readString` / `Files.writeString` | 存在しない |

したがって、クラス名が API 26 にあることだけでは足りない。`minSdk 26` の端末ではメソッド呼び出しが `NoSuchMethodError` になりうる。検証端末は API 37 であり、実機検証でもこの不整合はまだ露見していない。

また、`:app` の lint `NewApi` は 0 件だが、これは安全性の証拠にならない。`:core` は JVM モジュールなので、その lint は `:core` の JDK API 参照を検査していない。

## 決定

1. **`:core` の出荷対象コード（`src/main`）で使う JDK API は、`:app` の `minSdk` の Android API 面に存在するものに限る。** 現在の `minSdk` は 26 である。クラスだけでなく、メソッド・フィールドのシグネチャを Android SDK の `api-versions.xml` で確認する。ホスト JDK でコンパイルできること、JVM テストが通ること、API 37 の検証端末で動くことを判定基準にしない。
2. **`Files.readString` / `writeString` は使わない。** 文字列の読み書きには、API 面に存在する `Files.readAllBytes` / `Files.write` と `StandardCharsets.UTF_8` を使う。具体的なコード修正は別のコード変更で行う。
3. **今回の自動検査は、既知の禁止 API を見る denylist テストに限定する。** `:core/src/main` を対象に `readString` / `writeString` のメソッド名を禁止し、`:core:test` で再混入を検出する。`Files` 経由の呼び出しだけを探すと static import を見逃すため、メソッド名自体を対象にする。同名の独自 API やコメントまで止める副作用は許容する。`src/test` は APK に入らないので対象外とする。
4. **それ以外の API はレビュー時に確認する。** `java.*` / `javax.*` の参照を追加・変更した PR では、レビュー担当が次の表を使う。自動検査とレビューを併記し、レビュー済みの範囲以外を機械的に保証されたとは言わない。

| レビュー項目 | 合格条件 |
| --- | --- |
| 追加・変更した JDK クラス、メソッド、フィールドの洗い出し | PR で対象を列挙できる |
| Android SDK の `api-versions.xml` との照合 | 所有者とシグネチャを確認し、クラス・メンバーの `since` が `minSdk` 以下である。メンバーに `since` が無ければ所属クラスの値を継承する |
| XML に無い API、`since` が `minSdk` を超える API | 使用しない。ホスト JDK にあることで代替判定しない |
| テストのみで使う JDK API | `src/test` に限定されていることを確認する |

5. **`api-versions.xml` とクラスファイルを自動照合する方式は、現時点では採用しない。** 実装も、その検査が正しく合格・不合格を返すことの検証もまだだからである。後述の課題を解決し、陽性・陰性の検査例で確認できた場合に限り、別の ADR でビルド検査へ昇格させる。

denylist テストは本 ADR とは別のコード変更で追加する。テストの追加を確認するまでは、自動検査が導入済みとはみなさない。

## 検査の実効性

### 候補の判断

| 候補 | 判断 | 実際に守れるもの | 守れないもの |
| --- | --- | --- | --- |
| (a) クラスファイルの JDK メソッド参照を `api-versions.xml` と照合するスクリプトをビルドに組む | **現時点では採用しない**（実現可能性と判定結果が未検証） | 未実装なので、現時点では何も守れない | スクリプト自体、誤検出・取りこぼしの評価、ビルドへの組み込み |
| (b) 禁止 API の denylist をテストで見る | **採用する** | `src/main` に `readString` / `writeString` が再混入したことを `:core:test` で検出する | 他の新しい JDK API、依存ライブラリ内部、名前を動的に組み立てる反射呼び出し |
| (c) 何もしない | **却下** | — | 今回と同じ不整合をテストでもレビューでも拾えない |

### (a) について確認できていること、できていないこと

クラスファイルの直接メソッド参照には所有者・名前・記述子があり、`api-versions.xml` のメソッド名にも JVM 記述子が付く。したがって直接参照を突き合わせる設計自体は可能だが、実際にこのリポジトリで使える検査を作ったわけではない。**作れないと断定はしないが、現時点で「作れる」「網羅できる」とも書かない。**

少なくとも次の点は、実装して正負の例で確かめるまでは未検証である。

| 論点 | 検査に必要な確認 |
| --- | --- |
| 継承したメソッド | クラスファイル上の所有者と、XML がメソッドを持つ宣言側のクラスが異なる場合に、継承関係をたどって誤判定しないか |
| コンパイラ生成コード | `invokedynamic` などの参照まで同じ規則で判定し、合格すべきコードを不合格にしないか |
| 動的な呼び出し | 直接メソッド参照の列挙では、反射や文字列で指定する呼び出しを網羅できないことを検査結果の説明に反映できるか |
| APK に入るコードとの対応 | JVM クラスファイルの判定が、D8 等による変換後のコードに対して意図した意味を持つか |

(a) を将来採用するときの最低条件は、`Files.readString` を含む陽性例を確実に不合格にし、`Files.readAllBytes` / `Files.write` を使う陰性例を合格にし、その検査なしでは APK ビルドを成功とみなさない構成にすることである。これらを満たすまでは「`api-versions.xml` で自動検査している」とは記録しない。

## 理由

- 実行時に必要なのは Android 側の API 面であり、コンパイルに使う JDK の API 面ではない
- 既知の2メソッドだけでも denylist に入れれば、今回と同じ修正を後から元に戻す変更を JVM テストで止められる
- denylist の適用範囲を明示すれば、狭い検査を包括的な互換性保証と誤読せずに済む
- レビューでは XML のクラス・シグネチャ・`since` を確認対象に固定し、レビュー担当の記憶やホスト JDK の挙動に依存しない

## 帰結

- `:core` は JVM モジュールのまま維持し、高速な JVM テストという ADR 0007 の利点を失わない
- 現在分かっている違反は `readAllBytes` / `write` への置き換えで解消できるが、`readString` / `writeString` 以外も含めた `:core` 全体の API 26 適合は、別途全件確認するまで未検証である
- denylist は既知の2メソッドにしか効かない。新しい JDK API を使うたびに XML の確認が必要で、この人的な確認を省略できない
- **`:core` のテストが JVM で通ることは、Android で動くことを意味しない。** 少なくとも API 参照の検査と、`minSdk` 端末での確認は別の検証として残る

`minSdk` を上げる案との比較は次の通りである。

| 方針 | 効くこと | 限界・代償 |
| --- | --- | --- |
| API 水準に収める（本決定） | 既存の対応端末を維持したまま、API 面に合わせる | API の確認と検査が必要。denylist だけでは網羅できない |
| `minSdk` を上げる | 使いたい API がその水準の API 面に存在すると XML で確認できる場合には有効 | 対応端末を減らす。今回の2メソッドは android-36 の API 面にも無いため、26 から 36 へ上げるだけでは解決の根拠にならず、同種の再発も防げない |

## 代替案

### `:core` を Android ライブラリモジュールにする

Android ライブラリにすれば `:core` にも lint が届き、`NewApi` 等の API レベル検証を使える。包括的な自動照合を自前で作るより確実な案である。

採用しない理由は、ADR 0007 が確保した「Android SDK を必要としない軽い JVM モジュール」を失うからである。ローカル単体テスト自体は JVM で実行できても、モジュールの構築に AGP と Android SDK が必要になり、現在のテストの速さと環境の単純さを犠牲にする。まずは JVM 構成を保ち、既知の検査とレビューの範囲を明示する。

## 戻す基準

次のいずれかが起きたら、この ADR を置換する ADR で検査方法を変更する。

- (a) の自動照合を実装し、継承・コンパイラ生成コード・変換後コードの扱いと、陽性・陰性の検査例を検証できた
- denylist とレビューの範囲を超える不整合が再度見つかり、人的な確認では不足だと判明した
- API 水準の確認コストが、Android ライブラリ化によって失う JVM テストの利便性を上回った
