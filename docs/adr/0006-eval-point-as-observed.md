# 0006 評価点は再計算せず、画面の % は保存しない

- 状態: 採用
- 日付: 2026-11-27
- 置換: なし

## 文脈

設計の当初案は、画面から読んだ値をゲームの式で検算する前提を含んでいた（`score_pt` という名前、% を比率として保存する案）。wiki（学マスwiki）で仕様を確認したところ、次の状態だった。

- 評価点は「パラメータ分＋中間試験＋最終試験（順位・スコア換算）」の合計と説明されている
- ただしパラメータ係数が同じページ内に 2.1 と 2.3 の両方の記述がある
- スクショの実数（Vo1810＋Da2883＋Vi1740＝6433、評価点26,547）にどちらを当てても、試験分の上限（合計で最大 8,000〜8,900 程度）では差を埋められない
- 画面の %（19.5 / 42.0 / 35.8）は和が 97.3 で、実数比（28.1 / 44.8 / 27.0）とも、wiki のアイドル別比率（花海咲季は『初』全難易度 27/33/40）とも一致しない

## 決定

1. **評価点は観測値として保存する。再計算しない。** 列名は `eval_point`。`score_pt` という名前は試験スコアと混同するので廃止する。
2. **画面の % は保存しない。** 実数（Vo/Da/Vi）から比率を計算して表示する。
3. **評価点の比較には `param_total`（Vo+Da+Vi）を併記する。** 評価点の差を構成の差と読まないため。

## 理由

- 式が確定していないものを実装すると、外れたときに全件が静かに狂う。観測値なら常に正しい
- % は規則が分からない以上、保存しても解釈できない。解釈できない列は集計で事故を起こす
- 評価点は最終試験のスコアと順位を含むため、構成が同じでも数千点ぶれる。並び替えには使えるが、構成の良し悪しの指標には単独で使えない

## 影響

- 評価点の OCR に失敗した run は順位比較から外れる（「不明」として保存し、集計から除外する方針と同じ）
- 画面の % を後から使いたくなったら、そのときに規則を推定して別列で足す。既存データは壊れない

## 戻す基準

公式発表または十分な検証で式が確定したら、**検算用の別フィールド**として持つ。`eval_point` を計算値で上書きしない。観測値と計算値が食い違うこと自体が、式の誤りの検出手段になる。
